# Submission measurements

Measured on 2026-09-05 using Docker Desktop Linux x86-64 containers, Python 3.12.14, an AMD Ryzen 7 260 host with 31.26 GiB RAM, and 15.25 GiB available to Docker. Ollama uses CPU inference. Full model digest, package/settings provenance and corpus file hashes are included in [environment.json](environment.json) and the per-run JSON.

## Functional regression set

[JSON with answers and traces](functional/evaluation_results.json) · [CSV](functional/evaluation_results.csv)

20/20 cases passed the documented predicate. Classification accuracy, expected-source hit rate and risk agreement on eligible cases were 100%; required-concept coverage was 95.0%; cited-filename precision was 100%. General-guidance cases expect no risk, and unrelated text expects no retrieval. The denominator of retrieval hit rate is 19 relevant cases; risk agreement uses 17 risk-required cases.

This run uses **FakeLLM plus real BGE embeddings and Chroma**. Its 85.75% average verifier grounding heuristic is generated by dummy rules, not an independent grounding assessment. The fake answer includes retrieved text, making concept coverage comparatively easy. These development regression metrics do not estimate real-model or human-reviewed quality. No held-out test set or confidence interval is claimed.

| Mean retrieval stage (all requests) | 312.00 ms |

The runner cycles through all 20 questions five times. Five requests are direct out-of-scope responses, so the minimum is much lower than retrieval-bearing requests. The warm-up is one full graph invocation outside the measured window. Percentiles are lower order statistics over 100 observed request latencies, not confidence bounds. Throughput is completions per wall-clock second with four worker threads.

Retrieval accounts for about 97.4% of mean request latency here. This stage includes query rewriting, embedding, search, reranking and context validation; because the LLM is a dummy, this is evidence for a retrieval-stage bottleneck, not an isolated embedding microbenchmark. Model loading is the separate cold-start bottleneck. Stage means use all requests and include zero for skipped stages. Retries, if any, accumulate rather than disappear from timings.

Two concrete optimization experiments:

1. Cache normalized-query embeddings or final retrieval results with an index-version key. Measure repeated and unique workloads separately; invalidate on corpus/model updates. This targets the measured retrieval cost without pretending that the current result already uses such caching.
2. Compare a smaller Ollama model and/or reduced context against the same functional cases, then measure real CPU latency and verification failures. Keep hardware, concurrency and corpus fixed. This targets real inference cost, which the dummy benchmark excludes.

Neither proposal is reported as a measured improvement. Cross-platform run differences and shared-host load are not controlled optimization experiments.

## Real-model diagnostic baseline

[Original failing smoke run](before-classifier-fix/evaluation_results.json)

The first two-case real `qwen3:8b` run exposed a problem not detected by dummy tests: both outputs were classified `unknown`, and the general question unnecessarily received Low (0/100). Both were correctly counted as failed end-to-end cases even though their LLM verifier approved them. Latencies were 313.81 and 292.75 seconds. This also demonstrates why a model judging its own answer is insufficient.

Inspection showed that the Pydantic schema allowed defaulted decision fields and the classification instruction did not adequately distinguish suspected incident type from proven compromise. The fix requires all structured output fields at the provider boundary, rejects incomplete decisions, clarifies general-guidance routing and extends explicit English data-export recovery. Two tests cover rejection of incomplete decisions and preservation of a complete no-risk decision.

The baseline is retained, not overwritten or blended into the final run. Its code hash differs intentionally. A final smoke run is kept separately in `ollama-smoke/`; it is a small development validation, not a full 20-case real-model evaluation or a 100-query real-model load test.

### Overestimation found during manual review

The [intermediate smoke run](before-risk-evidence/evaluation_results.json) passed its then-current predicate but assigned **Critical 85/100** to the customer-data export, despite only two supported factors totaling **High 45/100**. This was a genuine false positive missed by the broad accepted risk-level list and the model verifier; it is not presented as final quality evidence.

Risk extraction now requests per-factor verbatim excerpts instead of Boolean guesses, rejects excerpts absent from the incident, and records accepted quotes separately from deterministic keyword recovery. Extraction instructions explicitly prohibit inferring privilege, credential theft or a critical asset from an ordinary external account/cloud-storage reference. The English and Hungarian export cases now require exactly 45/100. Regression tests cover fabricated risk evidence, retained valid evidence and overestimation rejection. Verbatim matching still does not prove semantic support, so analyst review remains necessary.

## Final real-model smoke test

[JSON with final answers and execution traces](ollama-smoke/evaluation_results.json) · [CSV](ollama-smoke/evaluation_results.csv)

| Case | Final decision | Answer attempts | Total CPU latency | Concept coverage | Predicate |
|---|---|---:|---:|---:|---|
| `breach_01` | `data_breach`, High 45/100 | 3 | 978.24 s (16 min 18 s) | 3/3 | Pass |
| `general_01` | `general_security_question`, no risk score | 1 | 291.59 s (4 min 52 s) | 2/3 | Pass |

The export has exactly two enabled factors, with retained quotes `external account` and `downloaded a customer data export`; no privilege, credential theft or critical-asset factor is invented. Both revisions preserved the 45/100 score. Its first two verifier decisions rejected the drafts (0.30 scores), and the third accepted it. The trace retains each attempt's status and accumulated timing; only the final draft and final detailed verifier feedback are stored, so the earlier rejection reasons cannot be reconstructed in full.

Classification, source hit, eligible risk agreement and cited-filename precision were 100% on these two cases; mean concept coverage was 83.3%. The final model-verifier score of 0.95 is a self-estimate, not a human grounding measurement. Manual review found the general answer omitted an explicit lessons-learned point and used a more action-oriented template than an ideal explanatory answer. Valid retrieval lists also include tangential procedures: expected-source hit rate is not retrieval precision. The final export answer improves conditional credential rotation and recovery, but containment scope still needs analyst approval.

This run confirms the targeted classification, no-risk routing and overestimation fixes with the actual local model. It does not establish production quality, an interactive latency SLA, held-out accuracy, or quality across all 20 questions. CPU latency is a major practical limitation, and expensive verification retries are visible rather than excluded. Shared-host activity and stochastic model behavior are not controlled here; these are individual observations, not an optimization comparison. The final source and dataset hashes match the submitted functional and load runs.

## Reproduction and artifact scope

Use the root README commands. `--output-dir` keeps provider modes/runs separate. JSON records contain code and dataset SHA-256 hashes; the source hash normalizes CRLF/LF across Windows and Linux. `environment.json` records the image used at measurement time; a later documentation-only image rebuild can have a different image digest while retaining the same measured Python source hash.

The source corpus is original demonstration text. Filenames being valid does not prove claim-level support. The sample is small, synthetic and used during development. Operational quality still needs a held-out bilingual set and human review.
